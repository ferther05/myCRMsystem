# CRM 页面与角色交互模式

按本次页面选读。这里只组织已知业务信息，不替代后端授权、状态机或待定业务决策。

## 页面说明的最小信息

记录目标角色、页面目的、数据/API 来源、信息层级、允许的动作与前置条件、正常及失败反馈。涉及生命周期时附状态/动作对应与 BD 依赖；同一字段在界面和接口中使用同一名称及枚举。

简单页面可用文字或线框图确认布局；复杂流程才需要交互原型。原型的模拟点击、截图或样例数据只证明设计表达，不能作为真实 API、资金一致性或权限验证证据。

## 导航、登录与个人信息

- 按销售专员、销售经理、管理员的已确认权限组织导航，保留首页待办与常用业务入口。切换角色或重新登录后不展示旧身份的敏感内容。
- 登录、首次改密、会话失效与个人信息维护明确下一步。账号注册方式依 BD-12；不能因参考模板包含“注册”便加入公开注册入口。
- 无权限页面有可理解的反馈和返回路径。窄屏以可到达的菜单替代侧栏，不能直接隐藏全部导航。

## 客户列表、详情与跟进

- 列表优先展示识别客户、归属、状态和待处理问题所需字段；筛选与分页保持稳定，返回列表时按既有交互保留必要查询条件。
- 详情组织客户概览、联系人、有效跟进时间线、关联商机及预警。跟进表单包含方式、具体联系人、实质结果、后续动作时间；无效记录不表现为有效时间刷新。
- 协作人只看参与商机所需的联系人最小信息，不能以一个详情 Tab 绕过客户档案权限。L1～L5 展示与接口脱敏一致。

## 公海池与归属流转

- 展示允许可见的基础信息、脱敏联系方式、可领取状态及已确认额度信息。冻结、已被领取、额度不足与版本冲突分别说明原因。
- 领取成功按服务端结果更新列表；失败保留提示并允许重新获取状态。按钮禁用防重复点击，但界面说明不能宣称它保证唯一归属。
- 预警、回收、申诉、交接与原负责人重领依据已确认规则呈现；BD-01/03/04/08 等依赖未定时不假定状态跳转结果。

## 商机推进与协作

- “线索→跟进→报价→成交→赢单”各阶段保留区别，展示当前阶段、允许动作、缺失条件、理由及最近有效业务活动。
- 推进、回退、关闭、接管使用实际动作接口；不能设计成任意修改枚举的通用下拉框。报价/确认记录、责任人与协作范围按契约组织。
- 按 BD-01/02/11 处理待关闭、客户保护和跟进影响范围；编辑备注不会在页面上伪装为有效推进。

## 合同、签约资料与回款

- 资料按环节展示当前版、历史版、上传者、确认/驳回意见；经理确认明确指向具体版本。新版本对旧确认的影响依据契约。
- 签约进度展示必交/可选条件及阻塞原因，不能将“资料上传”直接显示为赢单。合同、客户及商机状态关联遵从 BD-02。
- 回款计划区分计划版本、期次、应收与已收；登记区分到账金额、日期、凭证和核销对象。部分核销、差异与结清依 BD-05，不自动补余额或按浮点数近似判断结清。
- 并发或重复提交失败明确反馈；刷新后以持久化结果为准，不靠前端乐观更新掩盖资金冲突。

## 待办、日志与看板

- 待办包含事件对象、原因、时间、可执行动作和处理结果；问题解除后的状态来自服务端。多接收人与解除范围依 BD-07。
- 日志按权限展示可追溯摘要与脱敏变化；附件下载与原业务对象保持独立鉴权。
- 看板按漏斗、业绩排行、回款统计和过程指标组织。每项标明口径、时间范围、角色数据范围、单位与必要的刷新时间。
- 零分母、没有记录与查询失败分别处理；样例数字不能替代真实统计。图表下钻维持同一数据范围，不能展示越权明细。

## 从设计到代码

页面与 API 依赖写入实际需求记录。按任务保留必要设计产出，避免每个页面重复生成一整套原型文件。正式实现检查可用的 API、组件和构建脚本；遇到接口缺失就记录依赖，不把可预览原型标为联调完成。
