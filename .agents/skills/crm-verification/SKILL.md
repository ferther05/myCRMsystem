# CRM 验证与阶段验收

读取 [阶段状态](../../../docs/development-status.md)、当前需求记录与相关 BD 决策；按改动选择 [关键验证场景](references/scenarios.md)，不把整份场景每次全部运行。

## 选择验证

- 普通业务规则使用 JUnit 5；HTTP 校验/权限/响应使用 MockMvc 或已有接口测试；事务、唯一键、条件更新与并发使用真实兼容数据库的集成测试。
- 页面流程使用 [playwright](../playwright/SKILL.md)；可重复回归测试按实际项目框架和用户需求落地，不把临时 CLI 浏览器脚本当完整测试套件。
- 并发压测用 JMeter 或明确可重复的并发工具。50个用户同时争抢一条客户至少断言一次成功、唯一归属、计数与记录一致；多个客户争抢再验证配额。
- Clock 控制 T1/T2/T3、阶段停滞、季度限次和7天交接等边界。测试隔离数据，不能改系统时间或使用生产客户作为 fixture。
- 性能阶段使用明确数据量、请求和机器条件报告延迟，万级数据是原验收规模；响应时间目标需定义，不能凭“感觉快”通过。

单元、API/数据库集成或完整浏览器流程需要设计用例时，读取 [测试设计](references/test-design.md) 的相应部分；性能与领取/金额竞争读取 [性能和并发](references/performance-checks.md)。用例、覆盖率分母、负载和结果以本项目真实契约与环境为准，不直接采用通用模板的固定百分比或 TPS。

## 相关代码审查

功能完成或用户要求审查时，按 [审查清单](references/review-checks.md) 核对相关编码/契约、安全范围、性能资源与状态事务。给出可核对的缺陷位置、触发条件和修复建议；不凑评分或将普通评审扩展为全系统威胁建模。审查不替代运行验证。

## 执行纪律

1. 从实际 pom/package scripts/运行说明得到命令。当前没有应用骨架时不报告业务测试已通过。
2. 先执行必要检查，失败定位并修复后重跑受影响检查。通过后只因新改动或未解决风险扩大范围。
3. 测试验证可观察结果、拒绝行为和持久化一致性，不只断言 mock 调用了某方法。
4. 记录工具版本、环境、命令、结果和证据路径；测试未执行就说明原因，未决规则用条件预期而非假定正确答案。
5. 只有满足阶段验收且依赖补齐时更新通过状态；临时简版、缺工具或未部署不能写成全部完成。

部署阶段核对空库初始化、配置模板、Nginx/API、JDK、任务、日志与备份恢复。准备文件可在当前授权内完成；实际远程部署/发布依用户授权执行。
