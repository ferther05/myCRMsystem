# CRM 性能与并发验证

性能验收、领取竞争或金额并发时使用；普通文案修改无需压测。

## 定义场景与环境

- 本项目面向 10～50 人销售团队，原验收要求包含万级数据列表与看板。并发人数不等于持续请求速率；根据实际操作组合、思考时间和任务明确负载。
- 记录 CPU、内存、JDK、MySQL/Redis、连接池、网络、构建版本、fixture 规模、角色、缓存冷热及测试工具。登录、列表、看板、写操作分开统计。
- 平均值、P95/P99、吞吐量与错误率目标由当前验收约定确定。参考模板的 500 用户、800 TPS、300ms 或优化百分比不是项目要求或实测结论。
- JMeter、明确可复现的并发脚本或已有性能工具按环境选择。PerfMon/ServerAgent 等监控插件只在实际需要且具备时使用，不自动安装远程服务。
- 使用隔离测试数据和明确目标 URL；写操作参数化，清理自己创建的数据，不读取或压测生产客户。

## JMeter 与指标

- 生成可被实际版本加载的完整 `.jmx`，验证解析、参数、身份和响应断言；UTF-8 无 BOM 是可用的跨环境选择。不要从不完整 XML 片段推断阶梯负载已正确实现。
- 阶梯加压需使用实际支持的线程组/调度方案，核对起始人数、增长间隔、稳态时间和退出策略；普通固定线程组的 ramp-up 不等同完整的多阶段阶梯加压。
- 先小流量确认返回正确业务结果，再执行目标负载。断言同时检查 HTTP 与业务 `code`，避免把返回 200 的业务失败视作成功。
- Duration Assertion 限制单个请求耗时；P95 是全部样本延迟的第 95 百分位。分别配置、统计及解释，不能将逐请求超时断言当作 P95 验收。
- 报告采样区间、预热/稳态、样本数、平均/P95/P99、每秒请求或事务数及分母。吞吐量单位明确，多个 HTTP 请求组成一个业务事务时不混用 RPS/TPS。
- 竞争场景中预期的“已被领取/版本冲突/额度不足”单独统计；它们与非预期 500、超时、数据库异常分开报告。不能把正确拒绝全部算性能故障，也不能删除故障样本后宣称零错误。
- 缓存冷/热场景分别记录并核对数据正确性、角色隔离及变更失效。测试期间命中率是测量结果，不自动要求达到固定 90%。

## 数据库竞争的验收

- 50 个用户争抢同一可领取客户：请求开始时间有重叠；汇总响应及异常；提交后查询唯一归属、计数和必要审计。预期唯一成功，其余按实际契约拒绝。
- 同一个专员并发领取不同客户：客户各自行锁不足以证明用户配额，检查总持有量、每日计数和事务失败补偿。
- 同合同不同期次同时登记回款：总额不能超过允许余额；对成功与拒绝结果及持久化明细、合同余额一并核对。
- 相同幂等身份重复回款：按契约处理重放或不同 payload 冲突；两笔合法同额同日回款不能自动合并。
- 并发资料上传或版本分配：版本号唯一、确认指向具体版本、历史资料保留；审计与业务提交结果一致。

并发正确性与系统容量是两种结论，分别给出证据。并发任务按 [test-design.md](test-design.md) 收集异常、限时等待和清理资源。

## 定位与交付

有异常时结合慢查询、索引、执行计划、GC、连接池和锁等待定位实际瓶颈。按观察到的证据提出改进，不默认增加微服务、读写分离或多节点，也不把连接池经验公式当本机最优配置。

报告保留实际 `.jmx`/脚本、结果文件、指标摘要和运行条件，说明失败、未执行及限制。容量外推需说明数据与假设；未经复测不得写出预计优化百分比或“线性扩容”作为成果。
