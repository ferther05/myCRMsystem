# 数据库与事务一致性

## 公海领取与归属

同一客户只允许一个人成功领取。UPDATE 至少校验目标 id、可领取状态、owner_id 为空、version，按受影响行数判断；失败不得继续写领取成功记录。

领取不同客户时也可能并发突破同一专员的持有量/每日额度。客户行乐观锁只保护客户，不保护用户额度。设计原子配额更新、合适的用户级锁或事务约束，并明确 Redis 计数与数据库失败的补偿。原负责人重领例外依据已确认规则处理。

客户归属、商机责任、持有量、必要审计一起维护；后置查询校验不是自动防超额方案。转移要检查版本和操作权限，不能覆盖同时发生的领取。

## 金额与幂等

金额用 BigDecimal，数据库用 DECIMAL。明确 scale、compareTo 与舍入，不能使用 double 后再转换。合同余额校验与回款插入同一受保护事务，两个不同期次同时登记也不能超额。

重复请求使用稳定业务幂等身份与数据库约束；同金额同一天可能是两笔合法回款，不能把它们自动当重复。明确幂等重放与不同 payload 冲突的语义。

部分核销、计划金额差异与结清依据 BD-05。未确认前不擅自把某期全额标已回款或用差异说明抵消合同余额。

## 资料与迁移

签约资料同环节版本号用唯一键或锁保护，不能靠 MAX(version)+1 无锁分配。保留旧版本并按具体版本确认；新版本是否撤销先前确认需有明确规则。

数据库和对象存储不是同一个事务。文件元数据失败时做受控清理或补偿，避免数据库引用不存在的文件。未授权/已回收用户不能通过稳定 URL 绕过下载鉴权。

## 审计与缓存

关键资金、归属和审批审计应可靠持久化；异步方案见 BD-06，不能凭 @Async 声称与事务一致。异步携带不可变操作者快照，不读取已清理 ThreadLocal。

缓存只在提交成功后失效；数据变更与删除缓存先后关系、缓存失效失败恢复要有明确策略。数据库事务不能回滚 Redis，避免隐式跨存储原子性承诺。
