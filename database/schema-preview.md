# CRM 数据库精简预览（毕业设计版）

日期：2026-10-17。**推荐 18 张表，原 54 张推荐表方案降为历史参考。**

按你的建议，允许适度耦合，减少拆表和管理页面，优先让系统容易理解、写完和演示。这是新的设计预览，还没有连接 MySQL、建库建表或执行 SQL。

先看下面的业务主线，再看每张表的用途即可。这里仅列主要字段，完整类型、索引和约束在生成 SQL 时补齐，不再展开上千行字段字典。

## 一、系统实际上做什么

```text
用户属于团队
      ↓
客户 → 联系人、跟进记录、提醒计划
      ↓
商机 → 推进阶段、上传报价、邀请协作人
      ↓
合同 → 上传和确认签约资料
      ↓
回款计划 → 分期安排 → 实际到账记录

审批、待办、附件和日志供这些模块共用。
销售看板直接统计上面的业务数据，不再单独建报表表。
```

一个客户可以有多个联系人、跟进记录和商机。同一时刻只有一个客户负责人；商机协作人另外记录。合同连接商机，回款连接合同。

## 三、本轮已确认的业务口径（2026-10-15）

这些口径已经由用户确认，后续字段、接口和 SQL 必须遵守；尚未决定的结构细节不会被代码自行猜定。

- 账号采用内部申请后管理员审核启用。初始化必须有一个可用管理员账号，并预置两个建议团队及其演示账号；不开放公众注册。
- 客户查重采用规范化名称＋主要联系人号码组合，统一社会信用代码（如有）唯一；同名但联系方式不同进入人工复核。
- 一个商机最多生成一个有效合同；重复购买应建立新的商机。一个客户可以有多个商机和合同。
- 报备审批通过后转入申请人的“私海·待首联”，T1 从审批通过时刻起算；首联和常规回收按经过时长计算，首联 48/72 小时、常规 27/30 天生成预警/达到回收时间。
- 商机完成签约确认后赢单，客户进入待合同和回款全部结束的保护状态；所有相关合同均已结清，或已终止且有权限的审批确认无应收，客户才成为永久“已成交”。存在未收或逾期款时仍受保护。合同、回款、归属和状态历史永久可追溯。
- 待关闭处理/审批期间暂缓回收，最多 3 天；到期自动升级给经理/管理员，裁决前仍受保护，不会仅因超时自动回公海。
- 关联商机的有效跟进只刷新该商机和客户的时间，不激活客户下其他商机；协作人只访问参与商机的必要范围。
- 已有回款后允许新建回款计划版本，只调整未收期次；有部分到账的期次也锁定。新版本说明差异并经经理审批，未收期次总额等于合同金额减累计实收；旧版本、期次和到账保留，互不重复计算，合同最终应收仍以合同金额为准。
- 关键业务审计与业务写入同事务提交；定时任务运行记录独立写入，单条任务业务变更使用小事务。
- 待办唯一键为 `todo_type + biz_type + biz_id + occurrence_key + remind_date + recipient_id`；同一事件的专员和经理待办分别独立完成，源问题解决时统一解除未完成待办。
- 任务使用 `Asia/Shanghai`，顺序为活跃度/停滞、逾期回款、提醒、待办、公海回收；逻辑批次为 `job_name + business_date`，重试通过 `attempt_no` 区分，补跑只处理失败记录。

上述内容只是设计口径，不代表已经建库或执行 SQL。

六个必选模块都保留：用户权限、客户联系人、商机、合同回款、销售看板、任务日志。减少的是独立表和配置层次，不把“成交”与“赢单”、计划回款与实际到账混在一起。

## 二、18 张表分别存什么

所有表都有自己的 `id`，业务表按需增加创建人、创建/更新时间和并发用的 `version`。下面不重复列这些公共字段。`xxx_id` 表示关联另一条记录；JSON 表示一小段结构化信息，不是新的数据库。

### 01. `sys_user` — 用户

- 用途：登录、个人资料、角色、所属团队和账号启停。
- 主要字段：账号、密码哈希、姓名、电话、`role_code`、`team_id`、启用状态、首次改密标志、领取日期/次数、当前持有量。
- 简化：一个用户一个角色、一个当前团队。角色固定为管理员、经理、专员；功能权限和字段脱敏规则在后端集中维护，不建角色、菜单、权限和成员关系表。领取计数由系统事务维护，不能在个人资料页面修改。
- 初始化：管理员账号由数据库初始化提供；内部申请由 `crm_approval` 记录，审批通过后才启用。初始化脚本提供“华东销售团队”和“华南销售团队”，每队含经理和专员演示账号；明文初始密码只保存在 Git 忽略的本地凭据文件。

### 02. `sys_team` — 团队

- 用途：经理查看本团队，专员查看自己的业务。
- 主要字段：团队名称、`manager_id`、启用状态。
- 简化：只做一层团队，没有部门树、多级组织和多团队成员关系；商机协作仍需单独授权。

### 03. `sys_config` — 参数与字典

- 用途：集中保存超期天数、领取额度，以及行业、客户来源等选项。
- 主要字段：配置类别、分组、键、值、名称、排序、启用状态。
- 简化：系统参数和普通字典共用一张表；角色、商机状态和资料类型仍由程序固定，不能通过改字典绕过业务规则。

### 04. `crm_customer` — 客户

- 用途：客户档案、当前归属、公海/私海状态、预警和回收判断。
- 主要字段：名称、信用代码、联系方式、来源、行业、等级、标签、`owner_id`、`team_id`、客户状态、公私海状态、冻结类型/截止时间/审批号、最后有效跟进时间、预警周期/时间、待关闭开始/升级截止时间、待关闭裁决状态、永久成交时间、申诉季度、归属序号、前负责人/回流优先截止时间。
- 简化：标签用一个小数组保存；预警、冻结和当前归属直接存在客户表。领取、交接、回收的历史放到统一操作日志，不另建公海记录、预警记录和归属历史表。
- 查重：规范化名称与主要联系人号码组合查重；统一社会信用代码（如有）单独唯一。同名不同联系方式只提示复核，不直接把两个企业合并。
- 终态：赢单后进入“待合同/回款结束”的保护状态；待关闭审批最多暂停 3 天，超时升级但继续保护；所有合同与回款结束后进入永久“已成交”，写入永久成交时间，不因普通超期重新进入公海。

### 05. `crm_contact` — 联系人

- 用途：一个客户下的多个联系人及决策链信息。
- 主要字段：`customer_id`、姓名、职位、电话、邮箱、生日、决策角色、是否主联系人。
- 规则：同一客户最多一个主联系人；联系人不会因为商机协作就全部开放给协作人。

### 06. `crm_follow_record` — 跟进与关怀记录

- 用途：展示客户时间线，记录有效跟进和已经完成的关怀。
- 主要字段：`customer_id`、可选 `opportunity_id`、`contact_id`、跟进人、记录类型、方式、内容、实质结果、下次行动时间、是否有效、可选提醒计划号及本次发生标识。
- 简化：不单建关怀记录表。普通备注或生日祝福不自动算有效跟进；有效时间由后端按规则更新，原记录保留。
- 影响范围：关联商机的有效跟进刷新该商机和客户的最近有效时间；客户级跟进不批量刷新该客户的全部商机。

### 07. `crm_reminder` — 提醒计划

- 用途：未来要做的跟进，以及生日、周年、周期关怀提醒。
- 主要字段：`customer_id`、可选 `contact_id`、提醒类型、内容、重复方式、下次提醒时间、本次发生标识、启用状态。
- 简化：跟进计划和关怀计划合并。计划是“何时要提醒”，待办是“本次提醒发给谁”；完成记录存到跟进表，周期计划再计算下一次时间。

### 08. `crm_opportunity` — 商机

- 用途：管理客户的销售机会和阶段推进。
- 主要字段：`customer_id`、名称、负责人、团队、阶段、活跃度、预计金额/成交时间、报价金额/时间/附件号、客户确认结果/时间/附件号、最近有效推进时间、关闭原因。
- 简化：当前报价和当前客户确认直接存在商机表；旧文件在附件表、关键修改前后值在日志中保留，不建单独报价表、确认表和阶段历史表。阶段与活跃度仍是两个独立字段。
- 合同关系：一个商机最多一个有效合同；客户的重复购买建立新的商机。

### 09. `crm_opportunity_collaborator` — 商机协作人

- 用途：记录谁参与了哪一个商机，以及业绩分成。
- 主要字段：`opportunity_id`、`user_id`、协作角色、分成比例、加入/退出时间。
- 规则：同一人不能重复成为同一商机的有效协作人；分成总和由后端校验。协作授权只覆盖参与的商机和必要资料。

### 10. `crm_contract` — 合同

- 用途：保存合同、签约进度和回款汇总。
- 主要字段：合同编号、`customer_id`、`opportunity_id`、负责人/团队、名称、合同金额、签署/到期日期、合同状态、签订进度、回款状态、已收金额、当前生效计划号、业绩归属快照。
- 简化：签约追踪直接并入合同。业绩快照保存签约时的负责人、团队和分成，后续换负责人不覆盖历史业绩；已收金额是实际回款的汇总，不能手工直接改。
- 结束条件：合同状态至少区分签署中、履行中、已结清、已终止。已结清要求累计实际到账等于合同金额且无剩余应收；已终止只有在有权限的终止审批明确确认应收为零后才算结束。未收或逾期金额仍存在时不能结束保护。

### 11. `crm_payment_plan` — 回款计划版本

- 用途：记录某合同某一版未收款安排及审批结果。
- 主要字段：`contract_id`、版本号、该版本未收计划金额、依据资料版本号、变更说明、审批状态、提交/审批人和时间。
- 简化：每行就是一个计划版本，不再另建“计划主表＋版本表”。首版计划金额为合同金额；后续版本只列尚未收款的期次，其合计必须等于生效时合同金额扣除累计实收后的余额。新版本须说明金额/日期差异并经经理审批，批准后才切换合同的当前生效计划号；旧版本保留。

### 12. `crm_payment_period` — 回款期次

- 用途：表示一版计划下第几期、何时应收、应收多少。
- 主要字段：`plan_id`、期次编号、计划金额、计划到账日期、已收金额、回款状态。
- 规则：一期可以对应多笔实际到账。只允许调整没有任何到账的未收期次；已有部分或全部到账的期次保持原计划和金额不变。新版本生效后，旧版未收期次标记为已替代且不再计入当前计划，旧版和回款记录仍保留；不得迁移、复制或重复计算旧到账。

### 13. `crm_payment_record` — 实际回款

- 用途：登记实际到账，是回款统计的原始依据。
- 主要字段：`contract_id`、`period_id`、到账金额、到账日期、付款方式、凭证附件号、登记人、备注、请求幂等号。
- 规则：金额使用 `DECIMAL(18,2)`；不能重复记账、不能超合同剩余应收。汇总跨计划版本的原始到账，每笔只算一次；历史到账不因计划换版丢失。

### 14. `crm_approval` — 通用审批

- 用途：报备、申诉、接管、交接、长期维护、商机关闭、签约终止及明文导出审批共用。
- 主要字段：审批类型、业务类型/编号、申请人、审批人、状态、理由、提交/处理时间、冻结截止时间、批次号、少量类型专用数据。
- 简化：不同审批用类型区分，额外说明放小型 JSON；客户、金额和审批状态仍用明确字段。批量交接按客户逐条审批、共用批次号，不再建批次和明细表；不是通用工作流引擎。

### 15. `crm_attachment` — 附件与资料版本

- 用途：所有业务文件共用，包括报价、客户确认、合同资料和回款凭证。
- 主要字段：业务类型/编号、资料类型、版本号、文件名、私有存储路径、大小、上传人/时间、凭据说明、确认状态/意见、确认人/时间。
- 简化：文件信息、业务关联、签约资料版本及逐版本确认放在同一张表。七类合同资料由程序定义；前三类为签约必交，其余四类用于履约收款。不再建签约节点、资料版本、附件关联和确认记录表。
- 规则：新版本新增行，旧文件及其确认结果不覆盖；同一合同同一资料类型只取最新版本参与当前进度。最新版本未通过时，旧版通过不能代替它。下载由后端核对所属业务权限，不直接暴露存储路径。

### 16. `crm_todo` — 待办

- 用途：工作台展示逾期回款、长期未跟进、关怀、商机停滞和待审批等提醒。
- 主要字段：待办类型、业务类型/编号、本次发生标识、提醒日期、接收人、标题、处理状态、产生/处理/源问题解除时间。
- 简化：一行就是“某个人收到的一条待办”，不建事件主表和接收人关联表。唯一键包含类型、业务对象、发生标识、日期和接收人，同一天重跑不会重复提醒，也不会漏掉第二个接收人。
- 规则：个人点击处理只影响自己的行；源问题解决时，系统解除该问题对应的所有未解除待办。个人处理与业务问题解除分开记录，规则见 BD-07。

### 17. `crm_operation_log` — 操作与流转日志

- 用途：记录客户归属、公海领取/回收、审批、商机阶段和关键金额等操作历史。
- 主要字段：业务类型/编号、动作、操作者/当时团队、时间、请求号、归属序号、前后负责人/团队、交接只读截止时间、变更前后数据和原因。
- 简化：阶段历史、归属历史、公海流水、关键变更共用一张表。归属事件保存明确关系字段，供回流、领取限制和交接只读查询；不能只留下“某人修改了客户”一句话。
- 规则：关键业务审计与业务操作同事务写入，记录成功事实；不能修改或删除来改变业绩、归属和回款。日志输出仍需脱敏，不能代替实际回款表。定时任务运行日志单独记录，不用异步线程写入关键成功审计。
- 终态历史：成交、合同结束、回款结清、归属变更及公海动作都保留可查询链路；当前状态字段不能替代历史事件。

### 18. `crm_job_log` — 定时任务运行日志

- 用途：知道哪个扫描任务何时运行、处理多少条、失败哪些条，以及补跑结果。
- 主要字段：任务名、业务日期、逻辑运行批次、尝试次数、开始/结束时间、执行状态、成功/失败数量、失败业务编号和错误摘要。
- 简化：单应用实例内使用 Spring Task，任务定义在程序中；执行记录和少量失败明细合并，不建任务定义、运行明细、任务租约等表。日志可用于人工选择失败项补跑，业务写入本身仍要去重。

## 三、为什么这样就够了

- 角色与组织：固定三类角色，一层团队，用角色字段和后端权限映射体现 RBAC；不用做可视化权限编辑器。
- 客户：标签放客户表；预警和冻结保存当前状态；历史归属统一进日志。
- 商机：当前报价与客户确认放主表，旧文件和关键改动保留。
- 合同：签约进度放主表；资料和确认按附件版本保存。
- 审批与提醒：多种审批共用一张表，多种计划共用一张表，多种待办共用一张表。
- 看板：直接查询业务表，再用 Redis 缓存；不用提前建统计快照、业绩明细等表。

代价是几个模块共用审批、附件、日志，类型判断更多，字段权限由程序集中定义，JSON 中的额外说明不适合复杂统计。对本项目规模可以接受；不设计多角色、多级审批、多层组织，也不做多实例任务调度。

**确实需要独立的回款计划、期次和到账记录仍保留。**把它们都塞进合同一个字段，后面会难以处理分期、部分到账和换版，反而不方便你操作。

## 四、落地时只守住这些规则

1. 所有关键关联由后端校验；通用审批/附件的业务类型与编号不能由前端随意指定。核心专用关联可用外键，通用关联由服务层维护，不级联删除历史记录。
2. 客户领取要锁定用户额度、对客户做条件更新，归属与计数一起提交；重复领取、回款提交、资料版本和待办通过唯一键/幂等号去重。
3. 合同和回款金额使用精确小数；保存实际到账、审批和历史版本，不为简化直接覆盖。
4. 附件、审批、日志、导出和看板都按角色及对象范围检查权限。客户公海和协作场景只返回允许字段。
5. 跟进、阶段、签约、回款与回收有各自状态，阈值集中维护；普通字段修改不能伪装成有效跟进。
6. 日志与待办都有稳定业务身份。单实例任务防止重叠，单条失败隔离，重跑不产生重复业务结果。

这些规则后续在 SQL 和代码中实现，本次只做设计说明，未进行数据库或业务测试。

## 五、怎么开始写，哪些还没定

建议先实现用户/团队和客户/联系人/跟进，再做商机，随后合同与回款；审批、附件和操作日志随业务接入，最后补齐任务闭环与看板。不是先写完所有底层框架才能做第一张页面。

账号采用内部申请后管理员审核启用，申请记录直接使用 `crm_approval`，不另建注册表；不开放公众自助注册。初始化脚本必须提供一个完整可用的管理员账号，以及两个建议团队和对应演示账号。具体团队名称、账号数量和初始密码的本地保管方式在生成脚本前定稿。

仍需在对应功能编码前统一：报备审批与首次跟进顺序、首联预警/回收口径等；审计事务、待办唯一键、任务扫描顺序和业务时区已按 2026-10-17 推荐方案确认。BD-01、BD-02、BD-05 的待关闭超时、客户终态和回款计划换版口径已由用户确认。其余未决事项见业务决策记录，不要求现在一次答完。
