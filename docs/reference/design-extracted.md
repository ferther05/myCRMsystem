6: 1　项目概述
7: 1.1　选题背景
8: 1.1.1　行业现状与痛点
9: 客户资料分散：中小企业销售管理仍以 Excel 与微信为主，客户信息散落在个人手中，人员变动即造成客户流失。
10: 跟进无痕：跟进过程不留存记录，漏跟、忘跟、重复跟的情况普遍。
11: 业绩回款靠人工汇总：月底由财务手工统计成交与回款，管理层拿不到实时数据。
12: 超过六成中小企业未使用专业 CRM 系统。
13: 1.1.2　问题成因
14: 成熟 CRM 面向中大型企业，功能重、采购成本高、需专人运维，与中小企业「客户少、流程短、人手紧」的特点错位。
15: 市场上缺少真正轻量、低成本、开箱可用的方案。
16: 1.1.3　技术条件已成熟
17: Spring Boot 与 Vue 生态完善，前后端分离架构部署成本低，一台普通服务器即可运行。
18: 【技术要点】本部分不涉及编程实现，但需理解中小企业销售业务流程：线索获取 → 客户跟进 → 商机推进 → 成交签约 → 回款，以及「公海/私海」这种中国式销售团队管理概念。
19: 1.2　研究内容与目标
20: 1.2.1　业务主干
21: 把线索、客户、联系人、商机、合同、回款串成一条线上化、可追踪、可追溯的主线。
22: 1.2.2　管理机制
23: 重点研究与实现三项机制：商机状态机、公海客户分配与回收、任务与回款提醒。
24: 1.2.3　数据赋能
25: 提供销售漏斗、业绩排行、回款统计、过程管理指标四类看板，支撑经营决策。
26: 1.2.4　功能目标
27: 完成用户与权限、客户与联系人、商机、合同与回款、数据分析看板五大模块，实现销售全流程数字化闭环。
28: 1.2.5　技术目标
29: 掌握 Spring Boot、Vue 3、JWT 认证、ECharts 等关键技术，熟悉前后端联调与系统部署流程。
30: 1.2.6　交付成果
31: 完整源代码、数据库脚本、需求规格说明书、设计文档、毕业论文、部署使用手册。
32: 【技术要点】本部分为项目范围定义，不涉及编程；但需理解「研究内容」与「功能模块」的区别——前者回答研究什么问题，后者回答系统提供什么功能，撰写开题与论文时二者不可混淆。
33: 1.3　系统定位与边界
34: 1.3.1　系统做什么
35: 成交前的全过程管理：客户进入、归属、跟进、商机推进、签约过程追踪、回款跟踪、退出流转。
36: 1.3.2　系统不做什么
37: 不介入线下商务谈判与合同条款磋商（属于线下人际过程）。
38: 不做复杂审批流引擎（采用轻量审批：经理确认 / 驳回）。
39: 不做财务级账务处理（回款只登记与核销，不做凭证与税务）。
40: 1.3.3　适用规模
41: 面向 10 ～ 50 人规模的中小企业销售团队，单团队、单管理层级。
42: 【技术要点】需理解产品边界划分的思路：明确「做什么」与「不做什么」，避免需求无限扩张与过度设计；这是项目立项与开发时控制范围的关键能力。

156: 2　系统架构与基础设计
157: 2.1　总体架构
158: 2.1.1　分层结构
159: 表现层：Vue 3 单页应用，Element Plus 组件库，ECharts 图表，Pinia 状态管理。
160: 接口层（Controller）：接收请求、参数校验、调用服务、封装响应。
161: 业务层（Service）：业务规则、事务控制、状态机、权限校验。
162: 数据层（Mapper）：MyBatis-Plus 完成 SQL 映射与执行。
163: 存储层：MySQL（业务数据）+ Redis（统计缓存、字典缓存）+ 文件存储（附件）。
164: 2.1.2　前后端分离约定
165: 后端只提供 JSON 格式的 RESTful 接口，不做页面渲染。
166: 前端通过 axios 调用接口，统一在请求拦截器中附加 JWT 令牌。
167: 统一响应体：{ code, message, data }，前端在响应拦截器中统一处理异常码。
168: 2.1.3　鉴权流程
169: 登录成功后由后端签发 JWT（含用户 ID、角色、团队），前端存入 localStorage。
170: 后续每次请求在请求头 Authorization 中携带令牌。
171: 后端由 Spring Security 过滤器解析令牌、校验有效期与签名，还原用户身份。
172: 2.1.4　统一异常处理
173: 使用 @RestControllerAdvice 捕获业务异常与系统异常，统一返回错误码与提示。
174: 自定义业务异常类 BizException，携带错误码，避免到处写 try-catch。
175: 【技术要点】Spring Boot 分层架构（@Controller/@Service/@Mapper/@Configuration）、依赖注入（@Autowired/@Resource）、RESTful 设计规范、axios 请求/响应拦截器、JWT 三段式结构（Header.Payload.Signature）与签名校验原理、全局异常处理（@RestControllerAdvice + @ExceptionHandler）。

311: 2.4.4　乐观锁与逻辑删除
312: 客户、商机、合同、回款计划四类核心表统一增加 version 字段。
313: 所有更新操作均带 version 条件，影响行数为 0 即视为并发冲突。
314: 统一使用逻辑删除字段 deleted（0 正常 / 1 已删除），避免物理删除破坏历史关联。
315: 2.4.5　审计字段
316: 所有业务表统一包含 create_time、create_by、update_time、update_by、deleted 五个字段。

628: 分层调整的是「客户的回收阈值」，与商机保护期相互独立。
629: 无论客户属于哪一层，只要名下存在活跃商机，客户即进入保护期、不参与回收判定。
630: 【技术要点】枚举设计、策略模式（不同分层对应不同频率规则）、规则外置到配置表而非硬编码。
631: 4.8　跟进计划
632: 4.8.1　计划设置
633: 专员设置下次跟进时间与跟进方式（电话、微信、上门、邮件等）。
634: 4.8.2　到期提醒
635: 到期前由定时任务生成跟进待办，推送至专员工作台。
636: 跟进时间早于当前时间的，拒绝保存并提示。
637: 【技术要点】日期时间处理（LocalDate/LocalDateTime、时间比较）、定时任务扫描、待办生成接口复用。
638: 4.9　首次有效跟进
639: 4.9.1　有效跟进的四项标准
640: 沟通方式：电话、微信、上门、邮件等明确方式。
641: 沟通对象：对方的具体联系人（不能只写「客户」）。
642: 沟通结果：有实质性结论（不能是「未接通」「无回应」）。
643: 下一步计划：明确后续动作与时间。
644: 四项缺一不可，全部满足才判定为「有效跟进」。
645: 4.9.2　状态流转
646: 客户状态由「私海·待首联」转为「私海·跟进中」。
647: T1 倒计时结束，转入 T2 常规倒计时。
648: 4.9.3　不达标的处理
649: 记录仅作留痕，不重置倒计时，客户仍按 T1 计时。
650: 连续 3 条无效记录时，自动提醒专员与经理「跟进质量异常」。
651: 【技术要点】业务校验规则设计、状态机流转、时间戳更新、批量校验的性能考虑、正则或规则链校验四项标准（可用策略模式或简单 if 判断）。
652: 4.10　常规跟进与无效跟进处理
653: 4.10.1　常规跟进
654: 每次沟通后录入跟进记录，内容包含时间、方式、对象、结果、下一步计划。
655: 写入后重置客户 T2 倒计时，同时刷新该客户名下活跃商机的最后推进时间。
656: 4.10.2　预警解除
657: 客户若处于「私海·预警中」，产生新的有效跟进后预警自动解除，状态回到「跟进中」。
658: 4.10.3　无效跟进
659: 缺少沟通结果或下一步计划的记录仅留痕，不更新最后有效跟进时间。
660: 回收倒计时继续推进，不阻断用户操作，仅做标记与提醒。
661: 【技术要点】跨表更新与事务一致性、客户与商机的状态联动、「最后有效推进时间 = max(阶段流转时间, 有效跟进时间)」的实现方式。
662: 4.11　关怀提醒
663: 4.11.1　关怀事件
664: 客户生日、签约纪念日、回访周期、合同到期日。
665: 4.11.2　待办生成
666: 定时任务每日扫描，命中事件自动生成关怀待办并推送至归属人工作台。
667: 同一事件每天只生成一次，避免重复打扰。
668: 4.11.3　完成回写
669: 专员完成后写入关怀记录，进入客户时间线。
670: 【技术要点】日期计算（MonthDay 处理生日跨年）、定时任务、待办幂等（biz_type + biz_id + biz_date 唯一约束）。
671: 4.12　客户归属规则
672: 4.12.1　公海领取的并发控制
673: 采用乐观锁（条件更新 + 版本号），保证同一客户只会被成功领取一次。
674: 4.12.2　客户流回公海后的原专员优先接手
675: 客户被回收后的 7 天内，原专员可优先申请重新领取，不受持有量与领取频率限制。
676: 客户当前须无归属人；若期间已被他人领取，则申请失败，不可强行收回。
677: 领取记录中标注「原专员优先接手」，便于统计接手率。
678: 4.12.3　专员离职或调岗的协商转交
679: 由系统管理员发起，选定该人员及其名下客户与商机清单。
680: 管理员与该专员所属项目经理协商确定接手人，优先转交给同一经理下属的其他专员。
681: 无人接手或协商后无合适人选，则客户与商机一并流入公海池。
682: 已成交客户可选择保留给接手人而不进入公海，保证售后与回款连续。
683: 原负责人失去访问权限但保留 7 天只读便于交接；新负责人获得完整权限，持有量相应加减。
684: 全过程写入客户归属转移记录（原归属人、新归属人、原因、协商人、时间）与操作日志。
685: 【技术要点】乐观锁、事务批量处理（离职可能涉及大量客户）、批量更新的性能优化（分批提交、避免长事务）、审计字段自动填充、权限变更后缓存刷新。
686: 4.13　客户信息分级与脱敏
687: 4.13.1　字段分级
688: 按 L1 ～ L5 五级划分字段敏感度，详见 2.5.3 节矩阵。
689: 4.13.2　公海可见范围
690: 公海状态下仅展示 L1 基础信息与脱敏后的 L2 联系方式。
691: 目的：让专员能判断客户价值，又拿不到完整联系方式去私下联系，防止绕过系统。
692: 4.13.3　脱敏执行位置
693: 在后端服务层统一执行，明文不传到前端。
694: 页面展示、操作日志、数据导出三处走同一套规则。
695: 【技术要点】AOP 切面 + 自定义注解（@Desensitize）、Jackson 序列化扩展、反射遍历对象字段、权限矩阵存表 + 缓存、EasyExcel 导出时自定义 CellWriteHandler 实现列脱敏。
696: 5　商机管理（D 阶段）
697: 5.1　商机创建
698: 5.1.1　创建条件
699: 客户归属本人且状态为「私海·跟进中」。

701: 5.1.2　创建后的联动
702: 商机初始阶段为「线索」，初始活跃度为「活跃」。
703: 客户状态转为「私海·保护中」，暂停回收倒计时。
704: 同一客户可有多条商机，重复创建时提示已存在进行中的商机。
705: 【技术要点】主子表关联、状态联动更新（同一事务）、枚举初始化、防重复校验。

754: 5.3　阶段推进
755: 5.3.1　执行流程（11 步）
756: ① 接收请求参数（商机 ID、目标阶段）。
757: ② 校验操作人是否有推进商机的权限。
758: ③ 数据归属校验，判断是否在本人数据范围内。
759: ④ 按目标阶段的前置条件逐项判定是否达标。
760: ⑤ 校验该阶段迁移是否被状态机规则允许（防止非法跳转）。
761: ⑥ 更新商机当前阶段。
762: ⑦ 刷新最后推进时间，并将活跃度重置为「活跃」。
763: ⑧ 写入阶段流转记录（前后阶段、操作人、时间、备注）。
764: ⑨ 执行后置动作（延长保护期、启动签约追踪等）。
765: ⑩ 按事件生成待办。
766: ⑪ 写入操作日志，按阶段重新聚合并刷新缓存。
767: 5.3.2　失败处理
768: 任一步骤不通过则整个操作回滚，并明确提示缺少哪一项条件。
769: 【技术要点】长流程的编排（模板方法或责任链）、@Transactional 保证原子性、业务校验前置减少无效计算、日志与业务写入的事务一致性。

771: 5.4.1　约束条件
772: 目标阶段必须是当前阶段的相邻前一阶段。
773: 必须填写回退原因。
774: 跳级回退直接拒绝；已产生回款的商机不允许回退。
775: 5.4.2　回退后的联动
776: 销售漏斗同步回退，商机与客户状态联动复核。
777: 回退原因与流转记录一并留痕，供复盘分析。
778: 【技术要点】反向状态迁移的规则设计、审计留痕、统计口径的实时性处理（缓存失效重建）。
779: 5.5　输单与关闭
780: 5.5.1　输单
781: 客户明确放弃时标记输单，必须填写输单原因（价格、需求变化、竞品等）。
782: 5.5.2　关闭
783: 商机超过保护期由系统标记为待确认，经经理确认后转为关闭。
784: 5.5.3　后续影响
785: 该商机不再豁免客户回收判定。
786: 若客户名下已无其他活跃商机且无未结清回款，客户状态回到「私海·跟进中」并重新进入回收判定。

879: 5.9　协作人接管
880: 5.9.1　触发场景
881: 客户归属人 A 名下所有商机均终结，客户进入回收倒计时，但商机仍有活跃协作人 B 在跟进。
882: 直接回收会造成资源浪费，因此设计「先接管、后回收」。
883: 5.9.2　活跃协作人判定
884: 近 30 天内对该客户有有效跟进记录；或曾在该客户下创建过商机。
885: 仅建立过协作关系、期间无任何有效动作的，不视为活跃协作人。
886: 5.9.3　接管流程（6 步）
887: ① 系统生成「接管建议」待办，推送给活跃协作人并抄送销售经理。
888: ② 协作人提交接管申请，说明理由与后续跟进计划。
889: ③ 原负责人在职的需其确认；已离职、调岗或存在争议的由经理直接裁决。
890: ④ 客户归属由 A 转移至 B，写入归属转移记录。
891: ⑤ 原负责人持有量减一、失去访问权限（保留 7 天只读）；新负责人持有量加一。
892: ⑥ 客户退出回收判定，按新负责人的跟进时间重新计算 T2。

905: 5.9.5　与回收的先后顺序

910: 6　合同与签约追踪（E 阶段）
911: 6.1　合同记录生成
912: 6.1.1　成交后生成合同记录

914: 合同字段来源：商机金额、客户信息（名称、联系人、地址）、负责销售、数据字典与账期参数。
915: 6.1.2　生成后的联动
916: 合同状态初始为「待签署」，回写商机与合同的关联关系，客户状态保持「保护中」。
917: 生成「合同待签署」待办并写入操作日志。
918: 6.1.3　幂等控制
919: 同一商机名下已存在有效合同时，拒绝重复生成。
920: 【技术要点】数据组装（DTO/VO/Entity 转换）、BeanUtils 或 MapStruct 实现属性拷贝、幂等校验（唯一约束 + 业务校验）、事务一致性。
921: 6.2　启动合同签订追踪
922: 6.2.1　触发条件
923: 商机阶段为「成交」，权限与数据归属校验通过，且该商机尚未启动签约追踪。
924: 6.2.2　初始化内容
925: 创建签约追踪记录，初始化七个环节：签约阶段 3 个必交（报价单、需求确认书、合同），履约收款阶段 4 个可选（交付确认单、验收单、发票、回款凭证）。
926: 生成首个「待提交」待办；更新客户状态为「保护中」；写入操作日志。
927: 6.2.3　启动后状态
928: 商机进入签约追踪，暂停停滞判定并持续为客户提供回收豁免。
929: 重复启动被幂等校验拦截。
930: 【技术要点】模板化初始化（环节配置存入数据字典，避免硬编码）、批量插入、状态标记与联动的原子性。
931: 6.3　签约资料上传与版本管理
932: 6.3.1　上传要求
933: 专员按环节上传资料文件，并填写凭据说明（如「微信聊天截图，确认付款比例 3:4:2:1」）。
934: 6.3.2　版本管理
935: 系统按环节自动递增版本号（V1、V2、V3…），新版本上传后旧版本标记为「历史版本」。
936: 历史版本一律不删除、不可覆盖，仍可查看与下载。
937: 6.3.3　待确认推送
938: 上传后环节状态置为「已提交待确认」，推送确认待办给团队经理。
939: 【技术要点】文件版本管理设计（同一业务对象多版本）、文件命名规则（业务ID + 环节 + 版本号）、对象存储与数据库 URL 映射、文件下载鉴权（防盗链）。
940: 6.4　经理确认与转赢单
941: 6.4.1　逐环节确认
942: 经理可对任一环节执行确认或驳回；驳回必须填写原因。
943: 驳回后环节状态置为「已驳回」，专员收到待办并重新上传，驳回记录保留。
944: 6.4.2　转赢单的判定标准（4 条）
945: ① 合同定稿版已上传（与最终签署版一致）。
946: ② 双方签字盖章的扫描件已上传。
947: ③ 合同金额、签署日期、合同编号已登记。
948: ④ 团队经理已完成确认。
949: 签约阶段 3 个环节全部确认且上述 4 条同时满足，商机才转为「赢单」。
950: 6.4.3　转赢单后的联动
951: 商机退出签约追踪与停滞判定；客户状态转为「私海·保护中」，退出回收判定。
952: 销售漏斗与业绩统计同步更新；已确认环节的全部历史版本保留。
953: 【技术要点】审批式流程的轻量实现（状态机 + 待办，不引入工作流引擎）、多条件组合校验、事务与状态联动、统计缓存失效。
954: 6.5　履约收款资料登记
955: 6.5.1　登记内容
956: 按环节上传交付确认单、验收单、发票、回款凭证等履约资料。
957: 6.5.2　与回款的联动
958: 验收单确认后，提示专员登记对应期次的回款。
959: 6.5.3　可见性控制
960: 发票与回款凭证默认仅专员、经理与管理员可见（属 L4 商业数据）。
961: 【技术要点】可选环节的开关设计（按项目决定是否启用）、资料与回款计划的关联、权限分级。
962: 6.6　签约失败与终止
963: 6.6.1　触发场景
964: 客户放弃、条款谈崩、转入竞品、长期停滞等原因导致签约未能完成。
965: 6.6.2　处理方式
966: 由销售经理或系统管理员将签约追踪置为「已终止」，并填写失败原因。
967: 商机阶段同步转「输单」或「关闭」，活跃度转为「已终结」。
968: 未完成的回款计划同步作废或标记终止。
969: 6.6.3　后续影响
970: 商机不再豁免客户，客户重新进入回收判定。
971: 已上传的全部资料版本保留可查；失败原因计入统计；操作全程写入日志。
972: 【技术要点】状态终止的级联处理（追踪 → 商机 → 回款计划）、批量状态更新的事务、失败原因枚举设计与统计分析。
973: 7　回款管理（F 阶段）
974: 7.1　回款计划拟定
975: 7.1.1　计划字段
976: 字段
977: 说明
978: 期次
979: 第 1 期、第 2 期……
980: 金额
981: 本期应收金额
982: 计划日期
983: 约定到账日期，用于逾期判断
984: 触发节点
985: 签约 / 交付 / 验收 / 质保期满
986: 依据版本
987: 标记依据哪一版资料（未签合同时记「协商中条件」）
988: 状态
989: 待拟定 / 待确认 / 已生效 / 已变更
991: 7.1.2　拟定与确认
992: 由负责专员依据协商确定的付款条件逐期录入，提交后状态为「待确认」。
993: 经理确认后计划生效，各期到期前自动生成提醒待办。
994: 7.1.3　版本迭代
995: 计划可反复修改，每次修改新增版本、旧版本保留。
996: 合同正式签订后，可按最终合同条款再调整一次并完整留痕。
997: 各期金额合计与合同金额不一致时提示并需填写说明，不强制拦截（允许定金、折扣等差异）。
998: 【技术要点】主子表设计（计划主表 + 期次明细）、金额类型 BigDecimal 与精度处理、版本记录表设计、审批状态流转。
999: 7.2　回款登记与核销
1000: 7.2.1　登记字段
1001: 到账日期、到账金额、关联计划（核销到期次）、回款凭证、差异说明。
1002: 7.2.2　核销规则
1003: 每笔回款必须关联到具体的回款计划期次，核销后该期状态更新为「已回款」。
1004: 未收金额与回款率同步刷新；与计划金额不一致时需填写差异说明。
1005: 7.2.3　校验要求
1006: 金额不超过合同余额；重复提交按幂等处理；超额登记被拒绝。
1007: 【技术要点】事务与并发（同一合同多笔回款同时登记）、金额计算精度、乐观锁防止覆盖、核销逻辑（计划状态与明细的双向更新）。
1008: 7.3　逾期扫描与提醒
1009: 7.3.1　扫描规则
1010: 定时任务每日扫描回款计划，超过计划日期仍未登记回款的，状态更新为「已逾期」。
1011: 7.3.2　提醒推送
1012: 生成逾期提醒待办，推送给负责专员与销售经理。
1013: 同一计划每天只提醒一次，避免重复打扰。
1014: 7.3.3　解除方式
1015: 补登记回款后自动解除逾期状态。
1016: 逾期金额进入回款统计与数据看板。
1017: 【技术要点】定时任务 + 条件查询、状态批量更新、待办幂等设计、统计数据的缓存失效与重建。
1018: 7.4　结清与关闭
1019: 7.4.1　触发条件
1020: 合同累计回款金额等于合同金额，且签约阶段已完成确认。
1021: 7.4.2　处理结果
1022: 合同状态转为「已结清」，客户状态转为「私海·已成交」，永久退出回收机制。
1023: 业绩归属最终确定，进入成交客户统计。
1024: 【技术要点】聚合金额计算（SUM）、终态处理、客户生命周期的状态闭环。
1025: 8　客户退出与流转（G 阶段）
1026: 8.1　超期预警
1027: 8.1.1　触发条件
1028: 客户状态为「私海·跟进中」，距最后一条有效跟进记录达到 T2 减 T3（默认第 27 天）。
1029: 8.1.2　处理方式
1030: 生成预警待办推送专员，同时抄送销售经理；客户状态转为「私海·预警中」。
1031: 预警不重置倒计时，必须产生新的有效跟进或申诉通过才能解除。
1032: 已处于预警中的客户不重复生成预警。
1033: 【技术要点】定时任务、状态标记、待办去重、时间边界处理（等于第 27 天时触发）。
1034: 8.2　申诉延期
1035: 8.2.1　申请条件
1036: 客户处于预警期内；该客户本季度未提交过申诉；已填写申诉原因与后续跟进计划。
1037: 8.2.2　处理流程
1038: 客户状态转为「公海·冻结」，生成待审批单提交销售经理。
1039: 审批通过则延长 7 天并重置预警计时；驳回则立即进入回收判定。
1040: 申诉期间客户不可被他人领取；同一客户每季度仅限一次。
1041: 【技术要点】审批流简化实现、季度限次的判断逻辑（按年 + 季度分组统计）、冻结状态的互斥控制。
1042: 8.3　回收公海判定（六道闸）
1043: 8.3.1　六道闸明细
1044: 闸
1045: 条件
1046: 判定依据
1047: ①
1048: 客户归属为私海
1049: owner_id 非空，且状态 ∈ {待首联, 跟进中, 预警中}
1050: ②
1051: 时间达标
1052: 未首联：距今 ≥ T1（3 天）；已首联：最后有效跟进距今 ≥ T2（30 天）
1053: ③
1054: 预警已生效
1055: 至少生成过一次超期预警，且预警后未产生新的有效跟进
1056: ④
1057: 商机无有效保护
1058: 名下无「活跃」或「待关闭」的商机；签约追踪中的商机视为活跃
1059: ⑤
1060: 回款已结清
1061: 不存在状态为待回款 / 部分回款 / 已逾期的回款计划
1062: ⑥
1063: 不处于冻结状态
1064: 不存在审核中的申诉单、报备单或交接单
1066: 8.3.2　二次校验
1067: 执行回收前重新校验上述条件，防止扫描期间客户已被跟进、已被转出或已产生新商机。
1068: 8.3.3　回收执行
1069: 清空归属人、状态改为「公海·可领取」，写入公海流转记录（原归属人、回收时间、原因、最后有效跟进时间）。
1070: 回收原因枚举：超期未跟进 / 首联超期 / 商机停滞失效 / 离职批量释放 / 报备失效。
1071: 8.3.4　回收后影响
1072: 原专员失去访问权限；跟进记录与商机历史完整保留并随客户进入公海，新领取人可见（按分级展示）。
1073: 原专员持有量减一；回收次数计入过程管理指标，经理可在看板查看明细。
1074: 【技术要点】多条件组合查询与判定、条件构建器动态拼接、定时任务中的事务边界（避免大事务）、先查后改的并发安全（条件更新）、数据所有权转移与历史数据保留策略。
1075: 8.4　离职与调岗批量释放
1076: 8.4.1　触发与准备
1077: 由系统管理员发起，选定离职或调岗人员并确认其客户与商机清单。
1078: 8.4.2　处理方式
1079: 批量清空归属人，并将名下商机一并转出（转指定交接人，或进入公海·冻结）。
1080: 8.4.3　约束与留痕
1081: 不经过时间判定，立即生效；操作前二次确认。
1082: 已成交客户与签约追踪中的客户可选择保留给交接人，签约追踪记录随之转移。
1083: 操作前二次确认，全过程写入操作日志。
1084: 【技术要点】批量数据处理（分批提交、每批 500 条）、长事务风险与优化、二次确认的前端交互、操作日志的批量写入。
1085: 8.5　原专员优先重新领取
1086: 8.5.1　规则
1087: 客户被回收后 7 天内，原专员可主动申请优先重新接手。
1088: 不受持有量上限与每日领取次数限制；客户须当前无归属人。
1089: 8.5.2　失败情形
1090: 超过 7 天后按普通公海客户处理；若已被他人领取则申请失败，不可强行收回。
1091: 【技术要点】时间窗口计算、优先逻辑的判定、领取记录标记与统计。
1092: 8.6　流失标记
1093: 8.6.1　标记条件
1094: 专员提交申请，销售经理确认，并填写流失原因（价格、需求变化、竞品等）。
1095: 8.6.2　后续影响
1096: 退出回收机制与持有量统计，进入流失率与原因分布统计。
1097: 客户重新产生联系时，可通过领取或管理员恢复归属实现回流。
1098: 【技术要点】状态归档、统计口径设计（流失率 = 流失客户数 ÷ 期初客户数）、数据回流的状态恢复逻辑。
