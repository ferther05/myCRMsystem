53: ① 安装 JDK 17，配置 JAVA_HOME 环境变量。
54: ② 安装 Maven 3.9 并配置阿里云镜像（加速依赖下载）。
55: ③ 安装 MySQL 8.0，创建数据库 crm_system，字符集使用 utf8mb4。
56: ④ 安装 Redis 7.0，设置密码并验证连接。
57: ⑤ 安装 Node.js 18+ 与 npm，配置淘宝镜像。
58: ⑥ 安装开发工具：IDEA（后端）、VS Code（前端）、Navicat（数据库）、Postman/Apifox（接口调试）。
59: 2.1.2　环境自检
60: 命令 java -version、mvn -v、node -v 均能正常输出版本号。
61: Navicat 能连上 MySQL 并创建表，Redis 客户端能读写键值。
62: 2.2　设计定稿
63: 2.2.1　表结构定稿
64: 按 10 类表整理完整清单（用户权限、组织、客户、跟进、商机、合同签约、回款、流转归属、任务日志、配置）。

66: 每张表确定字段名、类型、是否必填、默认值、注释，形成 SQL 建表脚本。
67: 2.2.2　接口清单定稿
68: 按模块列出所有接口：路径、方法、入参、出参、权限要求。

203: 5.3　回收机制
204: 5.3.1　开发步骤
205: ① 先实现简版：按 T1/T2 时限 + 预警已生效两条判定，跑通回收链路。
206: ② 补齐六道闸：状态、时间、预警、商机活跃度、回款结清、冻结状态。
207: ③ 实现二次校验（回收前重新查一遍条件）。
208: ④ 实现回收执行：清空归属人、改状态、写流转记录（含原因）、生成通知待办。
209: ⑤ 实现超期预警：满足 T2 减 T3 时生成预警并置「预警中」。
210: ⑥ 实现申诉延期：预警期内提交，经理审批，通过则延长 7 天。
211: ⑦ 实现流失标记：专员申请 + 经理确认，退出回收机制。
212: ✔ 完成标准：构造一个满足条件的客户，次日定时任务执行后自动回收并出现在公海池。
213: ⚠ 常见坑：六道闸中「商机活跃度」依赖阶段 4 的活跃度计算，因此阶段 3 先做简版回收，阶段 4 完成后再回头补齐，避免阻塞。

226: 6.1.2　开发步骤
227: ① 商机创建接口：校验客户归属与状态，初始化阶段为「线索」、活跃度为「活跃」。
228: ② 定义阶段枚举与迁移规则表：只允许相邻推进、只允许相邻回退。
229: ③ 实现阶段推进的 11 步流程：权限 → 归属 → 前置条件 → 状态机规则 → 更新阶段 → 刷新最后推进时间与活跃度 → 写流转记录 → 执行后置动作 → 生成待办 → 写日志 → 刷新缓存。
230: ④ 实现前置条件校验：进报价需有报价记录，进成交需有确认记录。
231: ⑤ 实现阶段回退：相邻前一阶段 + 必填原因；已产生回款的不允许回退。
232: ⑥ 实现输单与关闭：输单必填原因；关闭需经理确认。
233: ⑦ 实现商机与客户状态联动：创建商机后客户转「保护中」，商机全部终结后客户回到「跟进中」。
234: ✔ 完成标准：商机可从线索一路推进到赢单；非法跳转被拦截并给出明确提示。
235: ⚠ 常见坑：状态机规则不要散落在各个 if 里。建议用枚举 + 规则表（迁移矩阵）统一管理，后期增加阶段时只改配置不改逻辑。
236: 6.2　活跃度与停滞
237: 6.2.1　开发步骤
238: ① 实现有效推进时间计算：max(最近阶段推进时间, 最近有效跟进时间)。
239: ② 实现定时任务：每日扫描未终结商机，按阶段停滞阈值判定活跃度。
240: ③ 实现四态流转：活跃 → 停滞 → 待关闭 → 已终结。
241: ④ 停滞时生成提醒待办给专员与经理。
242: ⑤ 待关闭需经理确认：确认则转已终结，驳回则恢复活跃并重置计时。
243: ⑥ 实现豁免规则：处于签约追踪中的商机跳过计算、维持活跃。
244: ✔ 完成标准：构造一条 25 天未推进的线索商机，次日任务执行后变为「停滞」。
245: ⚠ 常见坑：活跃度的判定必须用「有效推进」而非任意字段修改，否则用户随手改个金额就能刷新活跃度，机制形同虚设。
246: 6.3　多商机协作
247: 6.3.1　开发步骤
248: ① 协作人添加/移除接口，限制上限 3 人，记录协作角色与分成比例。
249: ② 权限校验扩展：判断当前用户是客户归属人、商机负责人、协作人还是经理。
250: ③ 协作人只能查看被授权商机、录入跟进，不可见客户完整档案。
251: ④ 实现协作人接管流程：活跃协作人判定 + 生成接管建议待办 + 审批 + 归属转移。
252: ⑤ 多个活跃协作人时按四维评分排序，由经理裁决。
253: ✔ 完成标准：A 的商机全部终结后，B 能收到接管建议并成功接管客户。

375: 十一　全程通用规范
376: 11.1　代码分层规范
377: Controller 只做参数接收与响应封装，不写业务逻辑。
378: Service 承载全部业务规则与事务控制，是唯一写 @Transactional 的地方。
379: Mapper 只写数据访问，复杂 SQL 写在 XML 中便于维护。
380: Entity 对应数据库表，DTO 用于接收前端参数，VO 用于返回前端数据，三者不混用。
381: 11.2　命名规范
382: 类名大驼峰，方法名与变量小驼峰，常量全大写下划线分隔。
383: 数据库表名与字段名小写下划线，表名用单数（如 customer 而非 customers）。
384: 接口路径采用 RESTful 风格：GET /customer/list、POST /customer/add、PUT /customer/update。
385: 11.3　Git 使用规范
386: 每完成一个可运行的功能点提交一次，不要攒一周再提交。
387: 提交信息写清楚做了什么：如「完成客户录入与查重」。
388: 在 dev 分支开发，阶段性完成后再合并到主分支。
389: 11.4　接口设计规范
390: 统一响应格式 { code, message, data }，code 为 0 表示成功。
391: 分页接口统一返回 { total, list }。
392: 所有需要登录的接口都要在权限表中登记权限点。
393: 接口参数一律服务端再次校验，不能只依赖前端校验。
394: 11.5　开发节奏建议
395: 每天开始前先明确当天要完成的具体功能点，不要边想边写。
396: 每完成一个模块先自测通过再往下做，避免错误累积。
397: 遇到卡住超过 2 小时的问题，先记录、跳过、继续做其他部分，避免阻塞整体进度。
